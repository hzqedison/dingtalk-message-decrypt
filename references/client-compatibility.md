# 客户端兼容性与多版本扩展

统一入口不等于任意版本可用。当前登记两套 Windows x64 MainFrame.dll 指纹与独立布局：
`9.0.2.261015001` 已有运行样本核验，`9.0.2.261018001` 已完成静态结构核验及合成测试，
尚待 DELL 原失败消息运行验收。不能仅修改版本号或添加哈希宣称支持。

## 给 agent 的一句话

遇到客户端升级导致读取失败，先运行 `python <skill>/scripts/client_doctor.py --dll "<实际 MainFrame.dll 路径>"`，
读取 JSON 中的 `reason`、`profile_id`、`dll_sha256`；未知指纹保留未解决，不能解释成缺密钥。

这个命令仅顺序读取指定的磁盘文件，不发现或打开进程、不调用 dws、
不读取正文或密钥、不需要 pefile/Crypto、不写缓存。
输出不含文件路径、账号、消息或密钥，可提供给维护者用于定位版本；
不要上传客户端二进制到公开仓库。
退出码 0 表示磁盘指纹已知；2 表示未知或文件不可读。
磁盘指纹已知不证明客户端已登录、进程内模块一致、密钥可用或正文恢复。

## 当前实现

- `scripts/client_compatibility.py` 集中保存已验证指纹与能力。
- `scripts/client_layouts.py` 保存不可变的具体布局；同批或同进程内切换选择不会修改全局偏移。
- 密钥、会话身份、驻留正文三个现有适配入口共用校验。
- 每个适配入口按文件指纹取得对应 profile 与布局；只有指纹登记、没有实现布局仍拒绝，
  不会自动复用旧偏移。所有路径使用实际选中的哈希写入证据。
- `local_crypto.client_compatibility` 保留指纹不匹配的结构化诊断。
  `unsupported_client_fingerprint` 发生在进程打开和密钥查找之前。
- 驻留正文后备路径对未知指纹提前停止，连可选 JSON 扫描也不执行。
- 纯明文、缓存与显式策略限制仍按原规则处理；不要清空策略记录或旧状态。

## 新版本接入与验收

1. 取得目标设备实际组件指纹和脱敏失败阶段，区分安装文件和运行中组件。
2. 核实变化涉及的结构、函数及布局，独立实现对应适配器。
   不能以版本字符串、相近版本、特征扫描命中或仅磁盘哈希登记代替验证。
3. 将经过验证的能力登记到新 profile。旧 profile 与适配器保留；
   新适配器需要显式选择自身 profile，未知 profile 必须拒绝。
   当前两版共享已核对的对象字段结构，分别使用各自的全局槽、代码和虚表地址。
   以后若对象结构改变，必须增加相应字段解析实现，不能只替换全局地址。
4. 测试未知指纹、错误布局、缺依赖、进程身份变化及能力缺失。
   使用合成样本做回归；旧版本测试也必须通过。
5. 在目标设备用原失败消息验收，按会话 ID、消息 ID、引用父 ID 对账。
   分别统计正文、引用、原始空字段、附件缺口和策略限制，
   并独立对比可用的原文证据。不能把安装成功或单测通过当作业务恢复。
6. 只提交源码、合成测试和脱敏说明；正文、密钥、缓存、原始验收输入留在本机。

`adapter_validation` 分别记录 `runtime_sample_verified` 与
`static_verified_runtime_pending`。前者也仅指已有样本验证，不能保证所有历史消息。
详细新版证据和 DELL 验收要求见 [261018001 核验记录](client-261018001-validation.md)。
